Why a side drawer — v3

Page behind stays visible

Operator can read existing rows while typing — useful when the new record references something on the list. Categories list visible while adding a new one means no surprises about duplicate names.

Lighter visual weight

No dim flash on open / close. The drawer slides in over only its own column and the list page scrolls behind. Reads as a tool attached to the list, not a takeover.

Fixed width for muscle memory

480 px regardless of which entity. Field grid is 2-col by default; Pricing collapses to 3-col only because each cell is narrow (₹100). Operator's eye hits the same place every time they open it.

Section anchors

Alt+1 / Alt+2 / Alt+3 jump to section, just like v1. Anchors are chips on the right of each section header — small, present but never demanding attention.

Trade-off vs v1 / v2

v1 (centred modal) is most familiar; v2 (workspace) is best for complex forms; v3 (drawer) is best when the list behind the form is part of the operator's context. Drawer is also the most natural for "+ new" stacking — second drawer can slide in over the first without losing the page.

Width compromise on small windows

Below ~960 px viewport, drawer takes 100% width and acts like a modal. The same component handles both — no separate codepath.
